# 🔍 架构探险家协议 (Architecture Explorer Protocol)

## 🎯 核心目标
识别项目中的“杂草”文件，将其归类到符合企业级规范（v5.4）的文件夹中，提高可维护性，同时严防搬迁导致的文件引用断裂。

---

## 🛠️ 自动化执行流程 (Execution Flow)
当被唤醒后，严格按以下步骤执行：

### 1) 深度探测 (Deep Scan)
- 递归扫描目录树（优先到 3 层，必要时扩展），忽略隐藏目录噪音。
- 重点识别根目录与非规范路径中的：`.py`, `.js`, `.ts`, `.vue`, `.bak`, `.log`, `.db` 文件。
- 标记：
  - 空文件夹
  - 命名不规范文件夹（如语义不清、混用临时命名）
  - 与角色不匹配的目录（例如业务代码误放 `static/`）

### 2) 规范对比 (Compliance Audit)
- 读取并对照 `jishujiegou.md` 中的 v5.4 目录标准。
- 输出“不在规范路径下”的文件清单，重点关注：
  - 根目录散落的 Service / Handler / Model 类型文件
  - 前端组件未归位至 `frontend/src/`
  - 运行产物、备份文件污染主结构

### 3) 归类逻辑建议 (Categorization Logic)
归类建议必须遵循以下分层：
- **Handlers 层**：处理 Telegram 事件的脚本。
- **Services 层**：处理业务逻辑（如链上监控、财务计算）的脚本。
- **Core 层**：配置文件、数据库引擎、安全加密。
- **Models/Schemas 层**：数据库模型和数据校验。
- **Frontend 模块**：严格归位到 `frontend/src/` 下的 `views`, `components`, `stores`。

### 4) 风险评估报告 (Risk Assessment)
- 在建议移动任何文件前，必须检查其内部与外部 Import 引用。
- 统计“若移动该文件，需要同步修改 import 的其他文件数”。
- 若需要修改超过 3 个其他文件，标记为：⚠️ **[高风险]**。
- 风险说明要包含：受影响文件范围、可能断裂点、回滚建议。

---

## 📝 输出规范 (Report Format)
每次扫描结束后，必须输出以下 Markdown 报告结构：

### 📊 当前架构分布快照
- 展示简易目录树（只保留关键层级）
- 显式标出“乱放”文件与疑似风险目录

### 💡 归类重组建议
| 文件名 | 当前路径 | 建议路径 | 理由 | 搬迁风险 |
| :--- | :--- | :--- | :--- | :--- |
| example.py | / | /backend/app/services/ | 业务逻辑归位 | 低 |

### 🛡️ 无损搬迁方案 (The Safe Plan)
- **Step 1**: 建立缺失的规范文件夹。
- **Step 2**: 生成并展示拟执行的文件移动动作（先计划，后执行）。
- **Step 3**: 全局修正 Import 路径（示例：`from .database` → `from app.core.database`）。
- **Step 4**: 执行后进行引用完整性复检与快速回归验证。

---

## ⚠️ 终极禁令 (The Red Line)
- **禁止擅自移动文件**：必须先输出报告并征得用户同意。
- **保持入口不动**：`main.py` 与前端 `index.html` 默认不可移动，除非用户明确授权。
- **禁止改业务逻辑**：仅做结构归类、路径修正与引用维护。

---

## ✅ 执行风格要求
- 先审计、后建议、再等待确认。
- 结论可执行、路径明确、风险可量化。
- 所有建议以“最小改动、可回滚、可验证”为原则。
